# AGENTS.md

`rangi` — a tiny, zero-dependency, fully synchronous syntax highlighter (fork of Speed Highlight JS). It takes code + a language and returns self-contained HTML (theme colors inlined as `style` attributes) or ANSI for the terminal.

## Layout

- `src/highlight.ts` — the core: `eachToken()` (regex rule engine, callback based, internal), `tokenize()` (public wrapper returning `ShjTokenized[]`), `highlightText()` (tokens + line-number gutter), `codeToHtml()` (full block markup). It imports no grammar and no theme: both arrive per call, which is what makes `rangi/core` bundle nothing. Both renderers have two output modes: the default inlines the theme as `style` attributes, and `classes: true` emits `shj-`prefixed class names and no `style` attribute at all — the theme is then unused, which is why `ShjCoreOptions` requires it only in the other branch. The class contract is public API: the README documents every name, so renaming one or adding a wrapper element is a breaking change.
- `src/terminal.ts` — `codeToAnsi()` / `printHighlight()`, same tokens as 24-bit escapes.
- `src/core.ts` — the `./core` entry, re-exporting those functions as they are; their `languages` and `theme` options are required (`ShjCore*Options` in `src/types.ts`, the main option types with those two made required).
- `src/index.ts` — the `.` entry: the same functions, wrapped to fill in the bundled registry and `defaultThemes`. Custom languages are merged over the bundled ones, so they still win and still apply to sub-languages.
- `src/detect.ts` — `detectLanguage()`, scored regex heuristics. Nothing else in `src/` may import it: it is a public function the caller opts into, and a grammar reaching for it would put it in every bundle (`test/bundle.test.ts` fails if one does). A grammar picks its sub-language out of the code itself or leaves it plain.
- `src/languages/*.ts` — one file per grammar, default-exporting `ShjLanguageDefinition` (an array of `[match, type?, sub?]` rule tuples; a rule with a `sub` but no `type` leaves a hole, `[/…/g, , "js"]`). `src/common.ts` exports the shared rules (`num`, `str`, `strDouble`), imported and dropped into a grammar as is.
- `src/languages.ts` — static registry of every grammar; `ShjLanguage` is derived from it. It is the `./languages` entry too, so every grammar is also a named export under its exact registry key (the four that carry a `type` are assembled into `{ default, type }` there); a test asserts the exports and the registry stay in step. `aliases` is the second registry: the other names a grammar answers to (`yml`, `mjs`, `python`), holding the very definition they stand for and spread into `languages`, so an alias resolves as `lang`, as a `sub` and as a named export without the engine knowing about aliasing at all. It is kept apart so the canonical name of a language stays knowable — `ShjLanguage` excludes the aliases, which is what the maps keyed by language rely on; `ShjLanguageAlias` is derived from it. An alias that collided with a language name would export that name twice, so the entry would not compile.
- `src/themes/*.ts` — one file per theme (plain data: `bg`, `fg`, `tokens` per token type); `src/themes/index.ts` re-exports them and derives `ShjThemeName`. Nothing validates a color, so `css-variables.ts` is a theme of `var(--shj-…)` references rather than colors — the one that covers all sixteen token types, and the one the terminal cannot render, since only a hex color becomes an escape sequence and anything else is left uncolored. `test/themes.test.ts` asserts the hex invariant over the others alone.
- `src/defaults.ts` — the only two themes the main entry pulls in (`default` light + `dark`, inlined as `light-dark()`).
- `src/tokens.ts` — the token types: `TOKENS` (names, in order) plus one `const` per type holding its index. A grammar refers to a type by the constant, which the bundler inlines to a digit; `tokenName()` in `highlight.ts` maps it back, so nothing outside a grammar ever sees an index.
- `src/types.ts` — all public types.
- `test/` — vitest, asserts exact output strings.
- `test/bundle.test.ts` — bundles `codeToHtml` out of `.` and `./core` with rolldown (a dev dependency) and checks the result against `BUNDLES`: its min+gzip `size`, and the `modules` of `src/` it is allowed to reach, which is what catches an import that leaks a theme or the registry into an entry that should not carry it. The size has 2% of headroom upward and none downward, so a shrink fails too: take the win by recording the size the failure prints. Whenever you do, re-measure the approximate figures in the README (two of them, the feature list and the core entry section) and the one below — they are prose, so nothing else keeps them honest.
- `test/languages/` — one file per grammar, each an inline corpus handed to `testLanguage()` (`_harness.ts`) plus the differences from the judges it is allowed to have. `_judges.ts` holds the cross check against Prism (`refractor`) and Shiki, both dev dependencies.
- `bench/` — mitata (a dev dependency), run with `node`, not Vitest. Everything measured is `codeToHtml`, the whole job: the layers under it do a subset of its work, so putting them side by side would read as a comparison when it is only a subtraction. `highlight.bench.ts` is the library on its own — every grammar in one pass (each corpus repeated out to 16 kB so no language counts for more than another), what the default options cost, and how the cost scales from 1 kB to 256 kB of one input. `compare.bench.ts` is the same corpus through Shiki on both of its engines, Prism, highlight.js, Lezer — the LR parsers CodeMirror 6 highlights with, through `@lezer/highlight`'s `highlightCode()`, the other end of the trade this library sits at and the one whose grammars have to be written whole, which is why its map is the shortest and why it and Speed Highlight between them decide which languages the default run shares — and Speed Highlight — the project this one is a fork of, which is why it is here: the row that says what the fork did rather than what a different design costs — over the languages all of them have, with what is and is not being measured written down at the top of the file, including that Prism, highlight.js, Lezer and Speed Highlight emit class names where we and Shiki inline the theme, so they are doing less work per token — which is why we enter twice, `rangi` inlining the theme and as the baseline every ratio is taken against, and `rangi (classes)` the same call with `classes: true`, emitting the markup those four do, so each side has a like-for-like row and nothing has to be discounted by hand — that escaping is Lezer's caller's job rather than `highlightCode()`'s, so it is done inside the timing there too, and that Speed Highlight's `highlightText()` is awaited inside the timing because its tokenizer is an `async function` that awaits itself through every sub-language, which is the cost being synchronous removes. It ends with a table of what each contender weighs and what it costs to start: each is bundled for the browser with rolldown out of the call that was just timed, through its own recommended entry points (Shiki fine-grained, Prism's components with their dependencies resolved from `components.json`, `highlight.js/lib/core` plus a grammar each, a `@lezer/<lang>` parser each with the dialects and the HTML nesting `@codemirror/lang-*` configures, Speed Highlight's single entry, which is the only one it has), and that one bundle is both weighed min+gzip and evaluated in a child process to time its cold start — ours through the main entry, so that row carries the whole registry where the others carry only the languages of the run, except Speed Highlight, which ships pre-bundled with every grammar inlined and so is counted off the specifiers left in its code rather than off modules a bundler can name. The cold start cannot be taken in-process: `_judges.ts` has already imported Shiki, and one process loads `shiki` once, so the second engine would be timed against the first one's module cache. Timing the bundle rather than the source also keeps `src/`'s forty-odd TypeScript files from being stripped one by one in our own row, which costs twenty times what the built entry does. Both take `--lang js,ts` to split the run into a benchmark per grammar; without it, one pass. `profile.bench.ts` is the third, and the only one that is not mitata: it runs the same workloads under V8's sampling profiler (`node:inspector`, warmed first, 100 µs apart) and reports where the time went rather than how much of it there was — self time per function, per source line (from the profiler's own position ticks, printed with the line of source), and per call path with `eachToken`'s recursion collapsed — writing the raw profile to `bench/.profiles/<scenario>.cpuprofile` for a flame graph in Chrome DevTools or speedscope. Its `--scenario grammars|corpus|scale|all` are the three shapes `highlight.bench.ts` times, and `--lang` narrows them the same way. What it cannot answer is which rule of a grammar is slow: V8 charges time inside a regex to the function that ran it, so every rule is part of `eachToken`'s self time — that question belongs to `pnpm bench --lang`. None of the three keeps a corpus of its own — `_corpus.ts` reads the one in `test/languages/`, by pointing the test files' `_harness.ts` import at the `testLanguage()` in `_collect.ts`, which only records. So a language added to the test suite is benchmarked without anything here being touched, and the corpus cannot drift from the one the grammars are asserted against.

Four build entries (`build.config.ts`): `.` → `src/index.ts`, `./core` → `src/core.ts`, `./languages` → `src/languages.ts`, `./themes` → `src/themes/index.ts`. Everything else must stay reachable only from those, so themes stay tree-shakeable. Nothing `src/core.ts` reaches may import `src/languages.ts` or `src/defaults.ts` — that is the whole point of the entry, and it is what keeps it ~3.4kB min+gzip for every export, ~1.5kB for `codeToHtml` alone, against ~13.2kB for the main one.

## Conventions

- Everything is synchronous and side-effect free; every language is bundled, nothing is lazily loaded or globally registered. Custom languages arrive per call via the `languages` option and are looked up before bundled ones.
- Unknown language / bad grammar degrades to plain text, never throws (`eachToken` swallows errors).
- Bundle size matters: prefer terse code, no dependencies, no runtime CSS.
- Imports use explicit `.ts` extensions.
- Token types are referenced by their constant from `src/tokens.ts`, never by name — a name in a bundled grammar is a missed byte. Adding a type means a new entry in `TOKENS` and a matching constant; a test asserts the two stay aligned. A custom language may still name its types, including ones that are not bundled.
- Adding a language: new file in `src/languages/`, register in `src/languages.ts` — both in the `export {}` block and in the `languages` object — add a row to the README table (+ `src/detect.ts` if detectable), and add `test/languages/<lang>.test.ts` — the registry test fails without it. An alias goes in `aliases`, in the alias `export {}` block, and in the `Aliases` column of that same row; it needs no test file of its own. Map it to a Prism and a Shiki grammar in `test/languages/_judges.ts` if either has one, to its highlight.js, its Lezer and its Speed Highlight grammar (or `null` each) in `bench/compare.bench.ts` — a Lezer parser it does not already have means a new `@lezer/*` dev dependency and a row in `LEZER_GRAMMARS`, so `null` unless it is worth one — and to its Linguist name (or `[]`) in `scripts/language-stats.ts` — those four maps are keyed by `ShjLanguage`, so a missing entry fails typecheck. The benchmarks pick the corpus up on their own.
- A grammar is only asserted against the judges where both of them agree with each other, and only on comments and strings. Anything else the corpus turns up has to be declared as a divergence with a reason, so no difference from Prism and Shiki stays unexplained; the ones marked `bug: true` are known defects, not decisions.
- Adding a theme: new file in `src/themes/`, export from `src/themes/index.ts`, add to `ShjThemeName` and the README table, then `pnpm theme` to regenerate the two committed figures — both pick the theme up off the `src/themes/index.ts` exports on their own, so neither script needs editing, but a stale file is a theme missing from the docs.

## Commands

`pnpm test` (lint + typecheck + vitest w/ coverage) · `pnpm dev` (vitest watch) · `pnpm build` (obuild) · `pnpm fmt` (automd + oxlint --fix + oxfmt) · `pnpm bench` (mitata, over the test corpus; `--lang js,ts` for a benchmark per grammar) · `pnpm bench:compare` (the same corpus through Shiki, Prism and highlight.js) · `pnpm bench:profile` (the same workloads under the CPU profiler: hot functions, lines and paths, plus a `.cpuprofile`; `--scenario all`, `--ms`, `--top`) · `pnpm language-stats` (rank the bundled grammars against GitHub usage; needs network) · `pnpm theme` (redraw both committed figures: `docs/themes-hero.svg`, the stacked deck at the top of the README, and `docs/themes.svg`, the card-per-theme grid in its Themes section). The two scripts behind it take `--out` and `--columns`, the hero also `--front <names>` — the themes that end each column, the only ones the deck shows highlighting code rather than as a name and a swatch strip. Both share `scripts/_svg.ts`, which highlights their samples with the library itself, so a figure cannot drift from what `codeToHtml` emits.
